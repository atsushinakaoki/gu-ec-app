# GUオンラインストア（学習用実装）

tech0 12期 Step4 個人課題 Lv3「コーディング」の成果物です。
自分で作成した要件定義書・設計仕様書・テスト仕様書をもとに、購入導線（商品一覧 → 商品詳細 → カート → 購入手続き → 注文確定）を実装しました。

> **本リポジトリは学習目的の非公式な実装です。**
> 株式会社ジーユーおよび株式会社ファーストリテイリングとは一切関係がありません。
> 商品名・価格・在庫はすべて架空のデータで、決済も実際には行われません（決済代行事業者への接続はスタブに置き換えています）。

**リポジトリ**: https://github.com/atsushinakaoki/gu-ec-app

---

## 1. なぜこの範囲を作ったか

要件定義書は商品検索・レビュー・店舗在庫・ORDER & PICK・返品交換・会員機能まで広くカバーしていますが、実装ではあえて **購入導線1本** に絞りました。

理由は、この課題で確かめたかったことが「画面の数」ではなく、**在庫を複数の人が同時に取り合ったときに矛盾が起きないか** だったためです。ECの難所は見た目ではなく、在庫・引当・決済・冪等性が絡む一貫性の担保にあります。浅く広く作ると、この難所を1つも通らずに終わります。

そのため、次の3つを設計仕様書どおりに作り切ることを優先しました。

- 在庫の引当と確定（悲観ロックによる同時実行制御）
- 注文確定の冪等性（二重送信で二重決済しない）
- 決済が「応答なし」で終わったときの後始末（補償処理と照会）

## 2. 技術構成

| 層 | 採用技術 |
|---|---|
| Frontend | Next.js 15（App Router）/ React 19 / TypeScript |
| BFF | Next.js Route Handler（`frontend/app/api/[...path]/route.ts`） |
| Backend | FastAPI / SQLAlchemy 2.0 / PyMySQL |
| DB | MySQL 8.4（tech0 12期 共有 Azure Database for MySQL） |

ブラウザは FastAPI を直接呼ばず、必ず BFF を経由します。ログイン用トークン（JWT）を JavaScript から読めない HttpOnly Cookie に格納するためで、設計仕様書 5.2 に対応します。BFF は業務判断を一切行わず（DS-614）、Cookie の中継と CSRF の確認だけを担当します。

```
ブラウザ ──/api/*──> Next.js（BFF）──> FastAPI ──> MySQL
```

### ディレクトリ

```
db/          スキーマ・初期データ・マイグレーション
backend/
  app/
    routers/     HTTPの入り口。業務判断は持たない
    services/    業務ロジック。HTTPを知らない
  tests/         単体テスト（DB不要）
  scripts/       結合・同時実行・変異テスト
frontend/
  app/           画面とBFF
  e2e/           ブラウザでの通し確認（Playwright）
```

## 3. 動かし方

### 3.1 準備

```bash
git clone https://github.com/atsushinakaoki/gu-ec-app.git
cd gu-ec-app
```

`db/.env.example` を `.env` としてリポジトリ直下にコピーし、パスワードを記入します。
**`.env` は `.gitignore` により追跡されません。絶対にコミットしないでください。**

```bash
pip install -r backend/requirements.txt
```

### 3.2 データベースの構築

```bash
python db/run_sql.py db/schema.sql   # 11テーブルを作成
python db/run_sql.py db/seed.sql     # 商品30件・SKU61件・会員3件
```

すでに構築済みの環境に後から列を追加する場合は、マイグレーションを順に適用します（新規構築時は `schema.sql` に含まれているため不要です）。

```bash
python db/run_sql.py db/migrate_001_checkout.sql
python db/run_sql.py db/migrate_002_summary_binding.sql
```

### 3.3 起動

```bash
cd backend
python -m uvicorn app.main:app --reload --port 8000
```

別のターミナルで、

```bash
cd frontend
npm install
cp .env.local.example .env.local
npm run dev
```

http://localhost:3000 を開きます。API仕様は http://127.0.0.1:8000/docs で確認できます。

## 4. 実装した範囲

### 4.1 画面

| カート `/cart` | 明細、数量、金額の内訳、引当期限 |


### 4.3 中心に据えた3つの仕組み

**(1) 在庫の門（悲観ロック）**

引当可能数は「在庫数 − 有効な引当数」で求めますが、この計算と引当の作成の間に他の人が割り込むと在庫がマイナスになります。そこで、在庫行を `SELECT ... FOR UPDATE` でロックしてからでないと引当を作れない構造にしました。在庫を触る処理は必ずこの1か所を通ります。

なお、ロックの取得順序は常に **カート → 在庫** に統一しています。順序が場所によって逆になると、デッドロックが発生します。

**(2) 注文確定の冪等性**

同じ `Idempotency-Key` で2回届いた要求は、2件目を新しい注文にしません。さらに、キーだけでなく注文内容のハッシュ値（fingerprint）も突き合わせ、同じキーで内容が違う要求は 422 で拒否します。

加えて、確認画面を出した時点のキーと fingerprint を `checkout` テーブルに記録し、注文確定時に両方の一致を要求します。「確認画面に出した内容以外は注文させない」ためで、金額が同じでも中身が入れ替わっていれば拒否されます。

**(3) 決済が「応答なし」で終わったとき**

決済の応答が得られない場合、それは失敗ではありません。決済代行事業者（PSP）側では成立している可能性があります。そこで応答なしは 202（決済待ち）として扱い、注文を `PENDING_PAYMENT` で保持します。その後、

- 利用者が注文詳細を開いたとき
- 次の注文を試みたとき
- バックグラウンドの定期照会（既定5分間隔）

のいずれかで PSP に照会し、成立していれば確定、否決されていれば在庫を戻します。

### 4.4 意図的に作らなかったもの

| 項目 | 理由 |
|---|---|
| クレジットカード番号の入力欄 | カード情報は PSP のトークン化により自社システムを通過しない設計（DS-582）。自社で受け取ると PCI DSS の対象になる。決済関数はカード番号を引数に取れない作りにしており、ログやDBに書き出す経路自体を無くしている |
| 商品検索・絞り込み・ランキング・レビュー | 在庫の一貫性という主題に関わらないため |
| 店舗在庫・ORDER & PICK | 同上。要件定義書では在庫を二重構造（オンライン在庫／店舗在庫）としているが、実装はオンライン在庫のみ |
| 会員登録・パスワード再設定 | 初期データの会員で購入導線を検証できるため |
| 購入履歴一覧・交換返品 | 注文1件の詳細表示までを範囲とした |
| カート明細の数量変更（PATCH） | 設計仕様書には定義があるが未実装。後述「既知の制約」を参照 |

## 5. テスト

| 種別 | 実行方法 | 結果 |
|---|---|---|
| 単体（DB不要） | `cd backend && python -m pytest` | 113件合格 / 13件スキップ |
| テストの強度確認（変異テスト） | `python scripts/mutation_check.py` | 仕込んだ12件のバグを12件とも検出 |
| 結合（実DBに接続） | `python scripts/order_flow_check.py` | 62件合格 |
| 同時実行 | `python scripts/concurrency_check.py` ※uvicorn起動中に実行 | 在庫1点に10人が同時注文して成功1件、を5回 |
| ブラウザ通し確認 | `cd frontend && python e2e/purchase_flow.py` | 16件合格 |

### 5.1 変異テスト — 「テストが通ること」を信じないための仕掛け

テストが全部通っても、それはテストが弱いだけかもしれません。そこで `mutation_check.py` を用意しました。**わざとコードにバグを仕込み、テストがそれを検出できるか** を確かめるスクリプトです。

実際、これで2件のテストの欠陥が見つかりました。

- すそ上げ加工の境界値テストが、1行のバグ（`<` を `<=` に変える）を見逃していた
- 支払方法の可否テストが、「拒否されたこと」だけを見て「拒否された理由」を見ておらず、間違った理由での拒否を通していた

### 5.2 同時実行テスト — ローカルで通っても本番DBでは落ちる

同時実行の検証は、実際の共有 MySQL に接続して行っています。これは重要でした。トランザクション分離レベルが REPEATABLE READ のままだと、**他のトランザクションが作った引当が自分からは見えず、在庫の二重引当が起きます**。ローカルの簡易な確認では気付けませんでした。

対策として、接続の分離レベルを READ COMMITTED にし、引当の読み取りにも共有ロックを掛けています。

## 6. 生成AIの使い方

この課題は「生成AIをガンガン使う」という宣言で取り組みました。私はコードを書けません。実装はすべて生成AIが書き、私は方針の決定・実行・判断を担当しました。以下は、その過程で分かったことです。

### 6.1 AIに書かせる前に、AIと仕様を決めた

Lv3は「要件定義書・設計仕様書・テスト仕様書を自分で作り、それをもとに実装する」課題です。この3つの文書も生成AIとの対話で作りましたが、**実装より先に、判断のつかない論点を洗い出して文書に残す** ことに時間を使いました。

たとえば「引当期限が切れる瞬間ちょうどに注文が来たらどうするか」「同じ引当が重複して登録されたらどう数えるか」といった論点です。これらは仕様として決まっていませんでした。ここを曖昧にしたままAIに実装させると、AIは何食わぬ顔でどちらかに決めて、決めたこと自体を報告しません。**AIは仕様の空白を埋めてしまう**、これが最大の落とし穴でした。

そこで、未確定の論点は「【未確定N】」として文書に番号を振り、実装では暫定の挙動を決めたうえで、**テストをスキップ扱いで残す** 方式を採りました。テストを実行すると、スキップの一覧として未確定事項が毎回表示されます。

```
SKIPPED 【未確定6】適用開始時刻ちょうど。実装は会員価格を適用する（開始時刻を含む）
SKIPPED 【未確定1】要求数量0。実装は ValueError を投げる
（他11件）
```

「決まっていないことが、決まっていないまま可視化されている」状態を作るのが狙いです。実務でも、決まっていない仕様を勝手に埋めて進むより、決まっていないと分かる形で残すほうが安全だと考えました。

### 6.2 別のAIにレビューさせた — 12件の欠陥

実装が一通り動いた段階で、**コード全体（7,258行）を1つのファイルにまとめ、Gemini と ChatGPT に「独立したレビュアー」として批判的にレビューさせました**。

結果は12件の指摘でした。書いたAI自身は、自分のコードの欠陥を見つけられませんでした。同じモデルに「レビューして」と頼んでも、自分の設計を正当化する方向に働きます。**別のモデルに、批判者としての役割を与える** ことで、はじめて出てきた指摘です。

| # | レビュアー | 重大度 | 指摘 | 対応 |
|---|---|---|---|---|
| 1 | Gemini | Critical | 同じカートへの同時投入で、明細が二重にでき、1明細10点の上限を突破できる | 修正 |
| 2 | Gemini | High | 上記を検出できないテストの欠陥（同時実行テストがCookieを共有しておらず、別人の競合しか試していない） | 修正 |
| 3 | Gemini | High | BFFのCSRF対策の抜け。Origin ヘッダが「無い」要求は素通りしていた | 修正 |
| 4 | Gemini | High | 決済待ちの注文の再送中に商品価格が変わると、「処理中」ではなく「内容が変更されました」が返り、顧客が再注文して二重決済しうる | 修正 |
| 5 | Gemini | Medium | カート明細の数量変更（PATCH）が設計仕様書にあるのに未実装 | 未対応 |
| 6 | ChatGPT | Critical | 異なる冪等キーで同時に注文すると、同じカートから注文が2件成立し二重決済されうる | 修正 |
| 7 | ChatGPT | Critical | 決済否決の補償処理が同時に走ると、在庫が二重に戻される | 修正 |
| 8 | ChatGPT | High | 確認画面と注文の中身が入れ替わっていても、同額なら注文できてしまう | 修正 |
| 9 | ChatGPT | High | 同じカート明細への同時追加で、論理的に同一の明細が複数行できる | 修正 |
| 10 | ChatGPT | High | 注文内容の確定後にカートを変更すると、注文・引当・カートの数量が食い違う | 修正 |
| 11 | ChatGPT | High | 決済タイムアウト後に利用者が注文詳細を開かなければ、在庫が永久に減ったまま残る | 修正 |
| 12 | ChatGPT | Medium | カート作成の競合で、正常な同時要求が 500 になりうる | 修正 |

11件を修正し、修正ごとに再発防止のテストを追加しました（結合テストの62件のうち20件がこれに当たります）。

指摘の質には差がありました。Gemini は「テスト自体が欠陥を見逃している」という、実装ではなく検証プロセスへの指摘を出しました。ChatGPT は同時実行の競合状態を網羅的に挙げました。**2つ使う意味があった** と考えています。

### 6.3 修正したことを、どうやって確かめたか

12件を「直した」と主張するには、直った証拠が要ります。そこで、**修正を1つずつわざと元に戻し、追加したテストが失敗するか** を確かめました。テストが失敗しなければ、そのテストは欠陥を捕まえていないことになります。

最初は8件中7件しか検出できませんでした。残る1件（決済待ちの明細への追加）は、同時実行テストの性質上、欠陥の経路を通らない回が多かったためです。順序を固定した確定的なテストに作り替えて、8件すべてを検出できるようにしました。

これが今回いちばんの学びです。**テストが通ったことは、欠陥が無いことを意味しません。** テストが欠陥を捕まえられることを、別途確かめる必要があります。

### 6.4 生成AIに任せて危なかったこと

正直に書きます。

- **「すべてのテストが通りました」という報告を、そのまま信じてはいけませんでした。** 実際には、テストが弱くて欠陥を見逃していた例が複数ありました（5.1、6.3）。
- **ローカルで通ったから大丈夫、も信じてはいけませんでした。** 共有の MySQL に接続して初めて、分離レベルに起因する在庫の二重引当が出ました（5.2）。
- **AIは、決まっていない仕様を勝手に決めます。** しかも、決めたことを報告しません。こちらから「決まっていない点を列挙しろ」と聞かない限り出てきません。

裏を返すと、**人間側が持つべきは「疑うための問い」** だと分かりました。コードが書けることではありません。「本番と同じ条件で試したか」「そのテストは、バグがあったときに落ちるのか」「決めていないことを勝手に決めていないか」。この3つを繰り返し聞くだけで、成果物の質は目に見えて変わりました。

## 7. 設計書の穴と、未確定事項の扱い

実装してみて、自分で書いた設計仕様書の不足が複数見つかりました。主なものを挙げます。

| 見つかった穴 | 実装での扱い |
|---|---|
| 確認画面で見せた内容と、注文確定時の内容の結び付きが定義されていない | `checkout` テーブルに確認画面時点のキーとハッシュ値を保存し、一致を要求する仕組みを追加（`migrate_002`） |
| 決済待ちの注文がある間、次の注文を受け付けてよいかが未定義 | 暫定で拒否（409）。【未確定13】として記録 |
| 決済待ちの注文をいつ照会し直すかが未定義 | 暫定で5分間隔の定期照会。【未確定14】として記録 |
| 補償処理（確定した引当を戻す）の状態遷移が定義されていない | CONFIRMED → RELEASED を補償専用の遷移として追加 |
| 税込表示で、明細ごとの端数処理と注文合計の端数処理が一致しない場合がある | 注文単位で1回だけ切り捨てる方式に統一。カート画面に1円のずれが生じうる旨を【未確定5】として記録 |

未確定事項は13件がテストのスキップとして残っています（5.1参照）。実務であれば、これは「事業側に確認すべき論点リスト」そのものになります。

## 8. 既知の制約

- **カート明細の数量変更（PATCH）が未実装** です。数量を減らすには、いったん削除して入れ直す必要があります。設計仕様書 6.2.1 には定義があり、レビューでも指摘（#5）を受けています。
- **決済代行事業者はスタブ** です。環境変数 `PSP_STUB_MODE` で成功・否決・応答なしを切り替えます。実際の決済は行われません。
- **定期照会を同一プロセス内のスレッドで行っています。** スタブがPSP側の記録をプロセス内に持つためです。本番であれば外部のジョブ、または PSP からの通知（webhook）に置き換えるべき箇所です。
- **画像は未配置** です。商品画像はプレースホルダを表示します。
- **共有DBを利用しています。** 同じ tech0 の共有サーバー上に `gu_ec_nakaoki` という専用データベースを作成しています。結合テストは会員1・2の注文とカートを削除するため、他のデータベースには影響しませんが、実行前に内容を確認してください。
